# Godot runtime review and worker scaling

Current human direction: investigate lag around forty workers, remove the rendering cap, and separate simulation scheduling from rendering. The lead is the sole developer. Investigation runs on GitHub, with bounded profiles rather than regression suites or local engine runs.

## Engine facts and application

- Godot calls `_process` per rendered frame. `_physics_process` requests fixed-frequency updates, normally 60 per second. These callbacks have different purposes; moving arbitrary expensive code to physics does not parallelize it. Trencho's authoritative event simulation now has one driver in the fixed callback; presentation stays in `_process`. Its actual wall-clock debt, Pause/1x/2x and atomic event transitions remain authoritative. [Processing documentation](https://docs.godotengine.org/en/stable/tutorials/scripting/idle_and_physics_processing.html).
- Physics and rendering still share the main loop by default. Godot bounds physics catch-up steps; a saturated main thread can still fall behind. Thus fixed scheduling removes our one-update-per-render policy, not every hardware dependency. Trencho retains unpaid wall-clock debt and must reduce the cost of the actual event work; changing callbacks alone cannot guarantee realtime operation. [Engine limits](https://docs.godotengine.org/en/stable/classes/class_engine.html).
- `max_fps=0` means uncapped; V-Sync can separately limit presentation to the monitor. The previous 30 FPS cap was our response to desktop near-freezes, not a gameplay rule or a Godot requirement. The requested configuration now uses zero FPS cap and disabled V-Sync. The manual four-worker pool setting is replaced by engine automatic sizing. [Engine settings](https://docs.godotengine.org/en/stable/classes/class_engine.html).
- A worker-pool setting does not distribute existing GDScript calls across cores. Tasks must actually be submitted. The game contained no `WorkerThreadPool`, `Thread.new` or process-thread-group use at the investigated revision. Our allocation and event work therefore remained synchronous. Godot also warns that splitting cheap tasks can be slower. [WorkerThreadPool](https://docs.godotengine.org/en/stable/classes/class_workerthreadpool.html).
- The active scene tree is not thread-safe. Detached expensive planning may suit background tasks, with input ownership, cancellation/generation checks, bounded results and authoritative commit on the owning thread. Concurrently mutating the live ledger, GUI and reservations would violate our current ownership. Adding threads to every worker is not an appropriate shortcut. [Thread-safe APIs](https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html).
- Godot supports nodes, Resources and data objects; there is no requirement to turn every simulated person into a node. Current measured costs come from our data access and update work. We should first remove repeated unused inspections, aggregate a synchronous view once, and update only visible UI. No ECS migration, plugin or language rewrite is justified by these measurements. This is our application judgment, not an engine-prescribed architecture. [Optimization guidance](https://docs.godotengine.org/en/stable/tutorials/performance/general_optimization.html).

## Evidence and first changes

The bounded profile at 1fa9c19 used explicitly controlled 8/40-worker populations in the actual authored session, not a gameplay grant or worker-arrival acceptance. At eight workers, repeat allocation cost about 10 ms; at forty, about 140 ms. Initial hauling-target admission rose from 41 ms to 340 ms. Workers-panel refresh rose from about 67 ms to 92 ms; Supplies stayed around 4–4.5 ms. Settled 0.1-second event advances were about 8–10 ms in this idle-hauler sample. [Baseline profile](https://github.com/TheInfinityIQ/Trencho_V4/actions/runs/41364857936).

Allocation inspected complete person mass despite using only status/qualification/assignment fields. It now uses the existing detached metadata query in those passes, preserving allocation ordering and safe handoff. The Workers panel now reads only the actual rear actor pool and a single-pass staffing summary, instead of exporting the full shared ledger and refreshing hidden systems. That summary retains the exact assigned/present/pending/retaining predicates and has no cross-frame cache.

The remaining allocation sort repeatedly inspected candidates. A one-pass minimum preserves the exact former preference: current duty, then Available, then least specialist rank, then lexical ID. Metadata is captured once only for the pure quota-planning phase; after actual reassignment starts, reads remain fresh. Repeated forty-worker allocation then measured about 3 ms, and its Workers refresh about 7 ms. [Changed profile](https://github.com/TheInfinityIQ/Trencho_V4/actions/runs/41365290608).

Four real workshop blueprints require 600 materials against the declared 500. This bounded shortage profile exposed complete person-mass reads even when no Emergency contender or eligible source stock existed. Those reads now occur only when actually required; real personal carrying limits and detached Emergency freight subtraction remain. Baseline four-site 0.1-second advances measured 69–71 ms; the repaired run measured 24–26 ms. Shortage-contention checks dropped from about 15 ms to 0.03 ms. [Baseline active profile](https://github.com/TheInfinityIQ/Trencho_V4/actions/runs/41365467728), [changed active profile](https://github.com/TheInfinityIQ/Trencho_V4/actions/runs/41365791366). These are separate GitHub runners and narrow synchronous timings, not native FPS or universal speedup guarantees. Initial assignment still has measurable reporting/route work.

The live clock check temporarily requested rendering at 5 and 120 FPS in CI, restoring zero afterwards. At 5, 1.066 seconds of wall time advanced 1.061 simulation seconds; at 120, 1.014 advanced 1.014. Remaining owed time was about 0.006 seconds. It also verified the shipped uncapped/V-Sync settings and active physics driver. [Clock check](https://github.com/TheInfinityIQ/Trencho_V4/actions/runs/41365665211). This verifies the changed scheduling under those short conditions, not unlimited throughput when the main thread is saturated.

## What engine suitability does and does not imply

Godot's own [data preferences](https://docs.godotengine.org/en/stable/tutorials/best_practices/data_preferences.html) and [node alternatives](https://docs.godotengine.org/en/stable/tutorials/best_practices/node_alternatives.html) support choosing data structures and object lifetimes for the actual workload. Typed dictionaries are not inherently wrong, nor does a Node per worker automatically improve allocation. Our repair reduces repeated global work and dictionary construction before considering a language or scene-model migration. The engine's [main loop source](https://github.com/godotengine/godot/blob/master/main/main.cpp) is a moving reference, not a substitute for the pinned executable's measured behavior.

The remaining 24–26 ms active advance can still produce noticeable main-thread spikes. Next investigation should attribute remaining actual route/source/store/event-boundary work for the human's job mix, rather than claiming that uncapped FPS or these first repairs settle every lag case. Background pure planning is a candidate only after proving its cost and detached ownership; moving the whole mutable simulation requires an explicit command/snapshot boundary and is a larger choice. Native Windows pacing, longer histories and the human's exact forty-worker activities remain unverified.
